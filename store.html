存储引擎

内容寻址存储（CAS）

所有下载的文件通过 SHA1 校验和存储到内容寻址存储中，路径为 ~/.local/share/moco/store/v1/。然后通过硬链接引用到目标路径。

工作原理

1. 下载文件 → 计算 SHA1 → 存入 store/v1/{sha1}
2. 检查目标路径 → 若不存在 → 硬链接 store/v1/{sha1} → 目标路径
3. 若目标路径已存在且 SHA1 匹配 → 跳过下载
4. 若目标路径已存在但 SHA1 不匹配 → 替换

核心优势

全局去重

相同的文件只下载一次。无论是多少个 Minecraft 实例引用同一个 library（如 LWJGL），磁盘上只存储一份副本，通过硬链接在多个路径呈现。

完整性验证

每个文件下载后自动与元数据中的 SHA1 进行比较。校验失败的文件会自动标记并重新下载，确保没有任何损坏的数据进入存储。

天然多实例隔离

每一个文件夹就是一个独立的 Minecraft 实例。不同于其他启动器为了共享资源而引入复杂的版本隔离机制，moco 的存储架构让这个矛盾自然消失 —— 文件共享由底层存储透明完成，多个实例之间互不干扰。

空间效率

硬链接不占用额外磁盘空间。不同于复制文件（每个实例一份副本）或软链接（源文件删除后失效），硬链接指向同一个 inode，任一路径都可以独立访问。

类比：pnpm 的全局 store

如果你熟悉 Node.js 生态，moco 的存储方案与 pnpm 的全局 store 原理完全相同：文件按内容 hash 存储，项目目录只保留硬链接。意味着：

  • 同一个 package 的不同版本不重复存储相同文件
  • 磁盘使用量显著低于 npm（每个项目复制一份）
  • 删除项目不影响共享存储中的文件

存储路径

~/.local/share/moco/
├── store/
│   └── v1/
│       ├── a1b2...        # SHA1 命名的文件
│       ├── c3d4...
│       └── ...
├── instances/
│   └── default/
│       ├── instance.toml
│       ├── libraries/     # 硬链接 → store
│       ├── assets/        # 硬链接 → store
│       └── versions/      # 硬链接 → store
└── cache/
    └── manifests/         # 缓存的版本清单
